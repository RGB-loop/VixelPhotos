# 产品 / 方案 / 架构 / 组件 / 交互 设计评审（综合）

基于：竞品调研（01）、架构评审（02）、UI 评审（03）、性能评审（04），以及本轮在真实库与合成库上的实测。

## 1. 产品设计

**定位是对的，且有真差异化。** “我不想整理，但我想找到”+ 全离线 + 中文优先 + 音视频片段可搜，在竞品里没有完全对位的产品（见 01）。

**最大的问题不是功能缺，而是 PRD 与现实脱节：**

| PRD 承诺 | 实测 | 差距 |
|---|---|---|
| 索引 > 5 张/秒（§5），1 万张可完成索引（DoD） | EmbeddingGemma 2 视觉编码 ≈ 3.3 s/张（M 系列 CPU，半数核心）→ 约 0.3 张/秒；1 万张 ≈ 9 小时 | **约 17 倍** |
| 机会窗口写的是 SigLIP 2（~80 ms/张） | 代码已换成 EmbeddingGemma 2（多模态统一空间，音视频可搜的前提） | PRD 未更新 |
| 搜索 < 1 s | 实测 20–30 ms（103 张库，语义开）；首次查询含预热 ~125 ms | ✅ 远优于目标 |
| 零网络请求 | 地图瓦片会联网；本轮已加白名单强制拦截并改 README 措辞 | ✅ 已修正 |

> 结论：搜索延迟是卖点；**首次索引耗时是最大的体验风险**——新用户导入图库后几小时内“搜不到”，很容易流失。

**建议（按优先级）：**
1. **两阶段索引**：先秒级完成缩略图 + EXIF + 文件名 + OCR（用户立刻可浏览、可按文字/文件名/日期搜），再后台慢慢跑向量；任务抽屉显示“语义索引 x%，预计剩余 y 小时”。现有队列优先级已接近这个形态，缺的是**对用户的明确预期管理**。
2. **按“最可能被搜”的顺序编码**：最近拍摄的、带 GPS 的、有人脸的先编码，而不是按入队顺序。
3. **空闲加速**：窗口失焦 / 屏幕锁定 / 接电源时用满核心（目前固定半数核心），用户回来时降回。
4. **评估 GPU/ANE 路径**：`device: 'webgpu'` 已有配置位但默认 CPU；或为视觉编码器单独提供 CoreML EP。这是唯一可能达到 PRD 数量级目标的路线。
5. 竞品对比中的 table stakes：搜索过滤 chips、离线地名、时间线 / 回忆、收藏 / 相册（见 01 §3）。
6. **结果可解释性**（本轮已做第一步）：网格角标标出“图中文字 / 文件名”命中，CLI JSON 带 `matchedBy`。

## 2. 解决方案设计

- **多通道 RRF（图片向量 / 片段向量 / OCR BM25 / 文件名）**：设计合理，等权 RRF 简单稳健；已去掉“视频代表帧被双计”的偏差。可改进：向量通道永远返回 K 近邻，弱相关的结果也会进前列——建议加距离阈值或按查询自适应截断，并为“精确模式”（只走 OCR + 文件名）留开关（Google Ask Photos 的教训）。
- **内容寻址（xxHash）去重**：正确且省算力；视频用 size+mtime+头尾采样的轻量哈希，权衡合理。
- **任务队列 + 可恢复**：好。本轮修正：embed 失败不再被吞（以前任务记 done、无向量、每次启动静默重排）；只有“模型未就绪”类失败会自动重排，坏文件留在任务面板由用户重试。
- **人脸聚类**：“宁可漏归不可错归”的阈值与批量聚类设计成熟，已有协作式让出事件循环。

## 3. 架构设计

```
Renderer (React, sandbox) ──IPC/vixel://──▶ Main (DB · 队列调度 · watcher · sharp 缩略图 · 人脸聚类)
                                             └─postMessage─▶ Inference utilityProcess (Gemma2 / SCRFD / MobileFaceNet / PaddleOCR)
CLI (Electron-as-Node, 只读打开同一库)
```

- **优点**：推理隔离到 utilityProcess 并降优先级、代际崩溃恢复、文本查询插队；`vixel://` 按 id 取文件、手写 Range。实测索引期间主进程事件循环无 > 50 ms 阻塞，IPC 全部 ≤ 1.2 ms。
- **本轮修复的架构问题**：启动全库重读重哈希（B1）、进度事件逐任务全表聚合（M1）、推理无超时可能永久卡死（B5 → 看门狗）、CLI 每次运行都执行 DDL/迁移（D3 → 只读）、渲染进程未开沙箱、隐私承诺无代码保障（D2）。
- **仍存在的设计债**：
  - `db.ts` 约 2000 行、~90 个方法的上帝模块。本轮已合并 4 份重复的内容 GC 逻辑；建议下一步按仓储拆分（photos / videos+segments / queue / faces+people / meta），质心计算移到 `core/face`。
  - 主进程仍做 sharp 解码与人脸聚类；当前规模下实测无卡顿，库到 10 万级时建议把缩略图生成也挪进 worker。
  - 网格分页是 OFFSET 分页；已加索引使首页 25 ms → 0.3 ms，但深翻页仍 O(offset)，长期应改 keyset 分页。
  - 向量 KNN 是 sqlite-vec 精确全扫（768 维 f32），10 万级以上建议 Matryoshka 截断到 256 维或二值量化预筛。

## 4. 组件设计（渲染进程）

- `App.tsx`（~700 行）仍连贯，但承担了选择、键盘、菜单、搜索、布局偏好五类职责。建议抽出 `useSelection`、`useItemActions`、`useKeyboardShortcuts` 三个 hook。
- 本轮已改：网格仅在列数变化时重挂（以前拖侧栏/滑块每帧重挂）、偏好写入防抖、键盘监听改 ref 模式只订阅一次、Inspector 详情请求防抖、人物页改协议直出 + 分批渲染、地图批量加点。
- 新增 `lib/mediaUrl.ts` 统一 `vixel://` URL 构造（带内容哈希破缓存），避免各处手拼。

## 5. UI / 交互设计

- **已改**：XSS（地图弹窗）、编辑时 Esc 误关详情、新搜索不回到顶部、无障碍语义（listbox/option、dialog、可 Tab 的侧栏）、全局焦点环、Home/End/PageUp/PageDown、模型未就绪在主窗口可见、低对比度提示文字、新导入照片卡在“破图”图标。
- **待做**：
  - 浮层焦点陷阱（目前只有 role/aria）。
  - 首次运行引导：选文件夹 → 说明“先可浏览、语义索引需要时间”→ 示例查询。
  - 零输入发现页（人物、地点、最近搜索、示例查询）与空结果改写建议。
  - 批量操作（目前多选只有“在访达显示 / 复制路径”）。
  - 日期格式跟随系统 locale（现在硬编码 zh-CN）。
